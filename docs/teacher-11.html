Activity 11 — teacher notes

Control from Anywhere. The arrow turns round: the board subscribes instead of publishing, and the class writes its first function and hands it over.

▶ Student page 📚 All teacher notes ← Activity 8 notes 📌 Pin reference
Keep this link to yourself. Unlisted and hidden from search engines, but the repository is public — anyone with the URL can read it.
This activity was written self-contained. It teaches WiFi, MQTT, the Adafruit IO account and the library from scratch, because Activity 10 did not exist when it was written. It does now — so roughly the first third of this page duplicates Activity 10, and can become a set of links to it whenever somebody has half an hour.

What is being taught

  • One idea, three moving parts, and they only work together. Subscribe (ask to be told), def (write a job down), and check_msg() (give it a chance to run). Take any one away and nothing happens — silently.
  • The headline is that the arrow turns round. Everything before today was the board talking. A thing that publishes can be watched; a thing that subscribes can be controlled.
  • The two ends never meet. The dashboard writes into a feed; the board reads out of it. That is why it works across a continent, and it is the sentence students remember.
  • First function in the module. Two things are new at once: writing code that does not run when you write it, and handing a name to somebody else so they can run it.
  • First while with a real question. Every earlier loop was while True. The WiFi wait is the first loop in the module that ends by itself, and the first place not is written rather than just read (Activity 6’s rule finally relaxing).
  • Three levels of indentation for the first time — inside the function, then inside the if inside the function.
  • No for loops, still, and no elif — available from Activity 9 on, but neither is needed here.

The pins, and the one thing the slide deck gets wrong

  • Red LED1 is GP11. Green LED3 is GP13. Same as Activity 1 and Activity 5, and confirmed against the board’s own GPIO layout sheet.
  • The Control from Anywhere PowerPoint says Pin(14) for the red LED, and 13 and 12 for yellow and green. Those numbers are shifted by one and do not match this board: on the LilEx5, GP14 is the buzzer. A student who types 14 gets a noise, not a light. If you teach from the deck, correct that slide first.
  • No new pins at all, on either route. Nothing to wire on the real board.

The exercise answer — never leave it in the dark

Green LED3 comes on whenever the order is OFF, so exactly one of the two is lit at any time. Two dark lights then means the board is not running.

The acceptance testFlip the switch both ways, then stop the program on purpose. Both dark only in the third case.
Why this exercise and not a second toggle It needs no new syntax at all — it is Activity 5’s two-branch if with one more line per branch — and it teaches something real: a device that can only say one word cannot tell you it is still alive. That is worth more than a second feed.

Going-further answers

TaskAnswer, in short
Print the time as welltime.ticks_ms(), or import localtime from time. The Pico has no real clock until something tells it the date, so a count of milliseconds since it started is the honest answer.
A second Toggle on a second feedA second subscribe with a second address, and one callback that decodes topic as well as message and compares it against each feed name.
Buzzer on each orderGP14, on then sleep(0.05) then off, at the top of the callback. Loud in a class of thirty.
Show the order on the OLEDActivity 7, unchanged: wipe, write, show, inside the callback. Needs ssd1306.py as well as the MQTT library.
Publish as well as subscribemqtt.publish(topic, value) in the loop, throttled — every tenth of a second is far too fast for a free account. Once every few seconds. Send the unrounded number; round only what is displayed.
Only act on a changeA variable holding the last order, compared before acting. Introduces the idea of remembering the previous value, which nothing in the module has needed yet.
Unplug the routerAn OSError out of check_msg, usually. A well-behaved device reconnects; doing that properly needs try/except, which this module has not taught — say so and leave it there.

A last will and testament — set_last_will before connect — is the professional answer to “how do I know it is still alive”, and it is a nice thing to mention in one sentence after the exercise. Do not teach it.

Before the lesson

  • Make your own Adafruit IO account and feed the night before, and run the whole thing once. Not optional. Everything after the account step depends on it working.
  • Decide the account question and say it out loud in the first minute. Own accounts (about ten minutes of the lesson, and needs email addresses), one per pair, or one class account. A shared account means one student’s switch controls everybody’s board — which is either a disaster or the best demonstration of the day, depending on when you do it.
  • Test the network on the day, with a board, in the room. A captive portal or a 5 GHz-only network kills the real-board route completely. Have a phone hotspot set to 2.4 GHz as the fallback and know its name and password.
  • Install umqtt.simple on every real board yourself, the way you did the screen and sensor libraries. It is not what the lesson is about.
  • Wokwi route: check Wokwi-GUEST reaches the internet from the school’s connection. It goes out over the same network the browser uses, so a school firewall that blocks outbound MQTT will block it too.
  • Give out board names. Seat numbers on the board before the lesson starts saves the confusing mid-lesson collision.
  • Have the key-safety line ready: it is a password, it is not to be shared, and Regenerate key fixes it if it escapes.
  • Thonny preset to MicroPython (Raspberry Pi Pico); pin reference open on every machine.

Teaching notes

  • Open with the switch and no board. Put your dashboard on the projector, click it, and let the class watch nothing happen. Then run one board. The gap between those two moments is the lesson.
  • Do the phone-on-mobile-data demonstration. Thirty seconds, and it is the only proof that will actually convince them the two ends are not on the same network.
  • The try-it widget on the student page is worth five minutes. Flip it before subscribing, then subscribe and press Ask once, then turn the loop on. Three failures and one success, with nothing to type.
  • Budget the account step properly. Sign-up, feed, key, dashboard and block is fifteen minutes with a class of beginners, and it is all clicking. Consider doing it as a whole-class walkthrough on the projector rather than letting thirty people wander.
  • Teach def away from the keyboard first. Write a recipe on the board, give it a name, and ask whether anything has been cooked. Then ask who is going to cook it.
  • Say “you never call this one” three times. It contradicts everything they know about writing a thing in order to use it.
  • The security line is part of the lesson, not an aside: your key is a password, and the feed is readable by anyone you give it to. It is the first time this module has produced something that other people can reach.
  • Safety rules unchanged: never 5V to a GP pin, never a power pin to GND, power off at SW5 before changing wires.

Verified during this build

  • Wokwi’s Pico W is the part board-pi-pico-w, running MicroPython v1.28. It is a different part from the plain Pico and is the only one with a network — picking the wrong one is a silent failure at the very first line.
  • Wokwi has no MicroPython package manager, so the library is a flat umqtt_simple.py project file, exactly as Activity 7 established for the screen driver. That is the only reason the import line differs.
  • The umqtt.simple in circulation raises MQTTException(5) for a refused login and asserts if subscribe is called before set_callback — both are in the troubleshooting table on the student page.
  • Write the client with keyword arguments, as the student page does. The deck describes it as MQTTClient(name, server, user, password); typed positionally, the username lands in the port slot and the connection fails in a way nobody can read.
