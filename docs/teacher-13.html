Pip

Keep this link to yourself. Unlisted and hidden from search engines, but the repository is public — anyone with the URL can read it.
This activity ships finished code, and that is a deliberate exception. Every other activity in the module has students type the program, because typing is how it lands. Here the program is three files of sensor plumbing they have already met, and the new learning is entirely in the cloud half. The one thing they type is config.py. Do not let the pack become an excuse to skip reading main_dashboard.py — the going-further tasks assume they have opened it.
There is a Wokwi route, and it has not been run yet. The starter project is a fork of Activity 10's (same custom weather chip, same Pico W) with main.py replaced and urequests.py added. It posts three readings instead of twelve; everything else is the same. Build it and run it once before a class uses it — the checklist is in wokwi/activity-13/HOW-TO-MAKE-THE-PROJECT.md in the repo, and the student page's Wokwi links say WOKWI-PROJECT-URL until you paste the real one in.

What is being taught

  • One idea: the middle is yours. Activities 10 and 11 borrowed somebody else’s service. Activity 12 removed the middle entirely. Today the class builds one. That three-step arc is the shape of the last three lessons and it is worth naming out loud.
  • The honest cost is taught alongside the win, exactly as in Activity 12: you need an account, the address is a password, Apps Script is slower than MQTT, and a deleted deployment fails silently. A student should be able to name one thing that got harder.
  • POST, contrasted with publish. Activity 10 handed a message over and never found out what happened. Today the board waits for an answer, so failures are loud. Both shapes are real; the class has now written one of each.
  • Named readings (JSON). One message, many values, each labelled — and the name is the only agreement between the board and the sheet. A misspelled name creates a new column in silence. This is the commonest bug in every system built this way and it is worth demonstrating live.
  • History is the payoff. A gauge answers “what is it now”; a sheet answers “what has it been doing”. Nothing earlier in the module could do the second.
  • Sampling interval as a design decision. One number in config.py decides how much detail survives and how fast the sheet fills. That is the exercise.
  • Reused, not re-taught: joining WiFi and the wait that ends by itself (Activity 10), the I²C sensor bus (Activities 7 and 8), the OLED (Activity 7), and the idea of a service in the middle (Activities 10 and 11).
  • Almost no new syntax, on purpose. The new difficulty is operational: deploying, authorising, keeping an address safe, and choosing a rate.

The cloud half, and what will actually go wrong

  • Apps Script must be opened from inside the sheet (Extensions → Apps Script). A script created from the Apps Script home page has no bound spreadsheet, and SpreadsheetApp.getActiveSpreadsheet() returns nothing. The symptom is a deployment that works, a board that reports OK, and an empty sheet. Expect this one every time.
  • Saving is not deploying. Editing the script changes nothing that the /exec address serves until Deploy → Manage deployments → edit → Version: New version. Editing the live deployment in place keeps the same address; a brand new deployment issues a different address, which is how half the class ends up with the board writing to one place and the dashboard reading another.
  • Who has access must be “Anyone”. A Pico cannot sign in to Google. That makes the long code in the middle of the address the only protection the sheet has, and the student page says so in a red callout. Say it again out loud.
  • The first visit has to be a human one. Open the /exec address in a browser once and clear Google’s “unverified app” warning before the board tries.
  • School Google accounts sometimes block Apps Script deployment entirely. Test this yourself, on a student account, before the lesson — not on your own staff account, which may have different rules. If it is blocked, deploy one script yourself and give the class the address; they lose ownership of the sheet but keep everything else.
  • Quotas. A consumer Google account allows roughly 20,000 URL-fetch-triggered script executions a day and about 90 minutes of total script runtime; a Workspace account gets more. At one reading every five seconds a single board uses about 17,000 executions in a 24-hour day, so a board left running overnight will hit the ceiling. One reading a minute — which is what the exercise asks for — is about 1,400 and is comfortable. Say so if a class is tempted to leave boards running.
  • A spreadsheet holds 10 million cells. With about 20 columns that is roughly 500,000 rows — a month at five seconds, four years at a minute.

The Wokwi route — what is different, and what to watch

  • Three readings, not twelve — temperature, pressure and humidity from the same custom weather chip as Activity 10. Use it, do not apologise for it. A Wokwi student's sheet is three columns wide and a board student's is twelve, from the same Apps Script: that is the "names decide the columns" idea demonstrating itself. If you have both routes in the room, point two of them at one address and put the gappy sheet on the projector.
  • The four settings sit at the top of main.py instead of in config.py, and only one of them is the student's to change — Wokwi's network is Wokwi-GUEST with no password.
  • The sensor's sliders are invisible until you click the green block while the simulation is running, exactly as in Activity 10. They are the best demonstration in the activity: drag the humidity slider and the number moves in the Shell, then the sheet, then the dashboard.
  • Wokwi freezes when its tab is not in front. Students will report that the rows "stopped". They did not; the clock did. This is on the student page too.
  • A 302 in the Shell is a success. Apps Script runs doPost and then redirects to a results page. urequests.py follows the redirect so you should see 200, but a 302 means the row landed.
  • If it runs out of memory, the TLS handshake is the cause and the one-word fix is allow_redirects=False on the post call — it skips the second handshake and reports 302. The full list is in wokwi/activity-13/HOW-TO-MAKE-THE-PROJECT.md.
  • It must be the Pico W (board-pi-pico-w). The plain Pico has no radio and fails at the first import, silently as far as a student is concerned.
Check the address inside the dashboard files before you hand them out LilEx5_Dashboard.html and LilEx5_Dashboard_History.html ship with a working /exec address already typed into API_URL. Whoever deployed that script owns the sheet it writes to, and anybody holding the file can add rows to it. Replace it with a placeholder before the pack goes out, or deploy a fresh throwaway script for the class and accept that the address is public. This is the same lesson the student page teaches, so it is worth being seen to follow it.

Before the lesson

  • Test the network with a board, not with a phone. 2.4 GHz, no sign-in page. A phone hotspot is a first-class fallback and should be presented as one, not as a rescue.
  • Deploy one script yourself and have the address ready. Students who lose twenty minutes on Google can use yours and come back to the deploying afterwards.
  • Try a student Google account end to end: make a sheet, open Apps Script, deploy, authorise. If any step is blocked you need the fallback above.
  • Decide whether history is in scope. The history view needs apps-script-history.gs pasted onto the end of the script and one line added to doGet. If the lesson is tight, skip it and demonstrate it yourself on the projector — the point lands just as well from a demonstration.
  • Put a sheet on the projector with a board already feeding it, so the class sees rows arriving before they start. This is the thing that makes them want to finish.
  • Have the pack on a shared drive, not on a memory stick going round the room.
  • Run the Wokwi project yourself, once, end to end, with the tab left in front, and confirm rows land in a sheet. It has not been run by anyone yet.

The one line that turns on history

Paste apps-script-history.gs at the bottom of the existing Code.gs, then make this the first line inside the existing doGet(e):

if (e && e.parameter && e.parameter.action === "history") { return getHistory(e); }

Then deploy a new version of the existing deployment so the address does not change. Test it in a browser tab with ?action=history&limit=5 on the end of your /exec address — you should get JSON with a rows array.

How to run the room

  • Do Part 1 together, on the projector, step by step. Deploying is four clicks and two of them are easy to get wrong. Going at one pace here saves the whole lesson.
  • Make them open the sheet before the dashboard. The rows are the lesson; the graphs are decoration. A class that goes straight to the pretty page thinks the dashboard is the thing they built, and it is not.
  • Break a name live. Change temperature to temprature in main_dashboard.py, run it, and let them watch a new column appear with no error anywhere. Thirty seconds, and it is the single most useful demonstration on the page.
  • Breathing on the sensor is the moment the abstraction becomes real — their breath, in a spreadsheet. Make sure everybody does it.
  • Ask who else can write to their sheet. The answer is “anybody with the address”, and it should come from them rather than from you.
  • Finish on history, even if it is only your own projected sheet. The arc of the whole module ends there: a light, then a loop, then a decision, then a screen, then a sensor, then the internet, then no internet at all, and now a record that outlives the lesson.

The exercise answer

Task: record one reading a minute, and make the dashboard open showing a whole school day of them.

Number one — the board

In config.py. A minute is 60 seconds, and the setting is in milliseconds:

REPORT_INTERVAL_MS = 60000

Upload config.py to the Pico again, then stop and run main_dashboard.py. The Shell should print one line a minute. That is the check — it needs no marking.

In Wokwi it is the same number, at the top of main.py, and there is nothing to upload — but they do have to press play again, and they have to leave the tab in front for a minute to see it work.

Number two — the dashboard

At the top of LilEx5_Dashboard_History.html. One reading a minute means one row a minute, and a seven-hour school day is 7 × 60 = 420 minutes:

const HISTORY_ON_OPEN = 420;

Any sensible school day is fine — 6 hours gives 360, 8 gives 480. What is being marked is the joining up: that the second number is derived from the first, and that the student can say what happens to it if the interval changes again.

The question to ask anyone who finishes early “You have just gone back to a reading every five seconds and left the dashboard alone. How much of the day is it showing now?” The answer is 420 rows × 5 seconds = 35 minutes. A student who can do that has the idea; a student who re-reads the file has not.

Common wrong answers

  • REPORT_INTERVAL_MS = 60 — seconds instead of milliseconds. Sixteen readings a second, and it looks like a network fault.
  • HISTORY_ON_OPEN = 7 or = 420000 — confusing rows with hours, or with milliseconds. It is a count of rows and nothing else.
  • Both numbers changed but config.py never uploaded — the commonest of the three, and invisible until you ask them to watch the Shell.

Going further — answers

TaskAnswer / what to look for
1. Chart inside the spreadsheetSelect the column, Insert → Chart. The point is that the dashboard was never necessary — owning the data means any tool will do. Worth saying out loud.
2. When does the sheet fill up?10,000,000 cells ÷ about 20 columns = roughly 500,000 rows. At one a minute that is about 347 days; at one every five seconds, about 29 days. The real answer to “what would you do about it” is: start a new sheet each month, or write only what you need.
3. Put the dashboard on GitHub PagesIt is a single self-contained file, so it works. And the /exec address inside it becomes public the moment it is pushed. The right answer is not to publish it as it stands — this task is a trap on purpose, and the discussion is the point.
4. Send a reading of your ownOne more key in the dictionary that main_dashboard.py hands to the reporter, with the Activity 9 soil percentage as its value. A new column appears in the sheet with no change to the Apps Script at all. The dashboard will not show a card for it — that needs a card added to the HTML, which is a good follow-on.
5. Two boards, one sheetAdd a "board" name to each message. It becomes a column, and the sheet can then be filtered or pivoted by it. The interesting difficulty is that the dashboard as written shows the latest row regardless of which board sent it.
6. Survive the WiFi going awayKeep unsent readings in a list, or append them to a file on the Pico, and post them when the connection returns. Raises ordering, duplicates and how much to keep — which is most of what makes real IoT hard, and is a genuinely open-ended task.
