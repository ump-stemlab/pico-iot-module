Exercise answer — all three LEDs

Code is shown as a picture — turn on JavaScript to see it.

The whole point of the exercise is the second clue: one nickname can only point at one pin. Students who reuse led three times end up with only the green LED lit, and that failure is worth letting them hit before you rescue them — it is the moment variables stop being decoration and start being a tool.

Accept any sensible names (led1/led2/led3, r/y/g, Malay names, anything). Push back only on names that lie, e.g. calling GP13 red.

Order does not matter. Some students will interleave name-then-switch-on per LED rather than doing all three names first — that is equally correct and worth showing to the class.

Going-further answers

TaskWhat happens / what to say
Only red and greenDelete the yellow lines, or just its .on(). Both work; ask which is tidier and why.
Name all three ledOnly the green LED lights. Each new led = Pin(...) overwrites the nickname, so it ends up pointing at GP13. The first two pins were never switched on. This is the single most useful misconception in the activity.
red.off() at the endThe red LED appears never to light. It does — for a few thousandths of a second. Sets up Activity 2, where sleep gives the eye time to catch it.
Pin(14, Pin.OUT)The buzzer sounds, continuously, until they stop the program. Loud in a full lab — you may want to demonstrate this once from the front rather than have thirty of them discover it at the same moment.

Before the lesson

  • A LilEx5 board and USB cable per pair; check SW5 (power) works on each.
  • Thonny installed, interpreter preset to MicroPython (Raspberry Pi Pico).
  • Open the Wokwi project on the projector and leave it up.
  • Have the pin reference open on every machine — students need it from here on.
  • Decide your route. Wokwi needs no hardware and no install; the real board needs both. Most classes do Wokwi first, boards in the second half.

The pin numbers students will get wrong

PartPinWhat happens if they miss it
LED1 red11—
LED2 yellow12Wrong colour lights, no error message
LED3 green13Wrong colour lights, no error message
Buzzer BZ114Loud continuous tone until they stop the program

The buzzer is the useful mistake: it is loud, obvious, and makes the “code must match the copper” point better than any explanation. Worth demonstrating deliberately once from the front — less fun when thirty students find it at the same moment.

The quiet mistake is 12 versus 13. Nothing errors; the wrong colour simply lights. Tell students that a program running without an error message is not the same as a program doing what they meant.

Teaching notes

  • Don't skip Wokwi. On the LilEx5 the LED wiring is inside the PCB, so students never see a circuit unless they build one. The Wokwi step is where the electronics is actually taught.
  • There is no print() in this activity. It was removed on purpose: the mission is “a pin makes a light come on”, and a message in a console window competes with that. print() arrives in Activity 3, where reading a button gives it a real job. If a student adds one, that is fine — praise it.
  • The most common typo is lowercase pin. MicroPython is case-sensitive; Pin is a class name. The type-it-here box on the student page catches exactly this.
  • led is not a keyword. Renaming it to lamp throughout is a great 30-second demonstration that variables are just nicknames — and it pre-teaches the exercise.
  • Comments are new in this activity. Students often think # lines do something. Ask them to delete every comment and re-run: identical behaviour. Then ask why anyone bothers.
  • Students expect led.on() to be temporary. Ask “what would make it stop?” — nothing does, which sets up Activity 2 (loops and sleep).
  • The three safety rules apply from day one: never join 5V to a GP pin, never join a power pin to GND, and switch off at SW5 before changing wires.
